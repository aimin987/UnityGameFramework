## 资源构建流程概述

`ResourceBuilderController` 是 Unity 游戏框架中负责资源构建的核心控制器，其构建流程始于 `BuildResources()` 方法的调用。该流程首先验证输出目录的有效性，并清理先前的构建产物，包括 `OutputPackagePath`、`OutputFullPath` 和 `OutputPackedPath` 等目录。随后，系统初始化构建报告（`BuildReport`），并触发 `OnPreprocessAllPlatforms` 事件，允许自定义处理器在所有平台构建开始前进行预处理。

构建流程的核心步骤包括：
1.  **资源加载**：通过 `ResourceCollection.Load()` 方法加载 `ResourceCollection.xml` 文件，该文件定义了所有待构建的资源及其配置。
2.  **依赖分析**：调用 `ResourceAnalyzerController.Analyze()` 方法，利用 Unity 的 `AssetDatabase` API 分析所有资源的依赖关系。
3.  **构建数据准备**：执行 `PrepareBuildData()` 方法，将资源信息转换为 Unity `BuildPipeline` 所需的 `AssetBundleBuild` 数组，并为每个资源创建 `ResourceData` 对象以管理其元数据。
4.  **平台化构建**：遍历所有选中的平台（如 Windows、Android 等），为每个平台执行独立的构建流程。

## 版本列表文件生成机制

在每个平台的构建流程中，`ResourceBuilderController` 会根据不同的输出选项生成相应的版本列表文件，其中 `GameFrameworkVersion.dat` 和 `GameFrameworkList.dat` 是两个关键文件。

### GameFrameworkVersion.dat 文件

`GameFrameworkVersion.dat` 文件在可更新模式下生成，其生成时机由 `ProcessUpdatableVersionList()` 方法控制，该方法在 `BuildResources(Platform, ...)` 流程的末尾被调用，前提是 `OutputFullSelected` 为 `true`。

该文件的内容结构由 `UpdatableVersionList` 类定义，包含以下核心信息：
- **游戏版本与内部版本号**：`ApplicableGameVersion` 和 `InternalResourceVersion`，用于标识资源包的适用版本。
- **资源资产列表**：包含所有 `Asset` 的名称及其依赖项的索引数组。
- **资源列表**：包含所有 `Resource` 的名称、变体、加载类型、长度、哈希值、压缩后长度、压缩后哈希值以及所包含资产的索引。
- **文件系统与资源组**：分别记录了资源所属的文件系统和资源组的名称及其包含的资源索引。

生成后，该文件会被压缩，并重命名为 `GameFrameworkVersion.{crc32}.dat`，其中 `crc32` 是文件内容的校验值。此文件在运行时的作用是让客户端能够从远程服务器下载最新的资源更新包，并通过校验值验证文件的完整性。

### GameFrameworkList.dat 文件

`GameFrameworkList.dat` 文件在单机模式或可更新模式的本地文件打包时生成，其生成时机由 `ProcessReadOnlyVersionList()` 方法控制，该方法同样在 `BuildResources(Platform, ...)` 流程的末尾被调用，前提是 `OutputPackedSelected` 为 `true`。

该文件的内容结构由 `LocalVersionList` 类定义，相较于 `GameFrameworkVersion.dat` 更为精简，主要包含：
- **资源列表**：仅包含 `Resource` 的名称、变体、加载类型、长度和哈希值。
- **文件系统**：记录资源所属的文件系统名称及其包含的资源索引。

此文件在运行时的作用是为打包在 `StreamingAssets` 目录下的本地资源提供一个快速的索引，使游戏框架能够在启动时快速加载这些只读资源。

## AssetData类与资源元数据管理

`AssetData` 类是资源元数据收集的核心数据结构，它被封装在 `ResourceData` 类中，用于存储单个资源文件（Asset）的详细信息。

`AssetData` 类包含以下关键属性：
- **Guid**：资源的唯一标识符，用于在 Unity 项目中精确引用。
- **Name**：资源的完整路径名称（如 `Assets/Textures/Icon.png`）。
- **Length**：资源文件的原始大小（字节）。
- **HashCode**：资源文件内容的 CRC32 校验值，用于检测资源是否发生变化。
- **DependencyAssetNames**：一个字符串数组，存储了该资源所依赖的其他所有资源的名称。

这些元数据在 `PrepareBuildData()` 方法中被收集。系统遍历 `ResourceCollection` 中的所有 `Asset`，读取其文件内容以计算 `Length` 和 `HashCode`，并通过 `ResourceAnalyzerController` 获取其依赖项列表，最终将这些信息封装成 `AssetData` 对象并添加到对应的 `ResourceData` 实例中。这种设计使得构建系统能够精确地追踪每个资源的状态，为增量构建和版本控制提供了基础。

## 依赖分析与文件系统分组

### 依赖分析实现

依赖分析由 `ResourceAnalyzerController` 类负责。在 `PrepareBuildData()` 方法中，系统通过 `m_ResourceAnalyzerController.GetDependencyData(assetName)` 获取指定资源的依赖数据。`ResourceAnalyzerController` 内部利用 Unity 的 `AssetDatabase.GetDependencies()` API 来获取一个资源直接或间接依赖的所有其他资源的 GUID 列表。这些 GUID 随后被转换为资源名称，并存储在 `AssetData` 对象的 `m_DependencyAssetNames` 数组中。此过程确保了构建系统能够完整地理解资源间的依赖关系，从而正确地打包和加载资源。

### 文件系统分组实现

文件系统分组是通过 `ResourceData` 中的 `m_FileSystem` 字段实现的。在 `ResourceCollection` 中，开发者可以为每个 `Resource` 指定一个文件系统名称。在构建过程中，`CreateFileSystems()` 方法会遍历所有 `ResourceData`，收集所有唯一的 `FileSystem` 名称，并为每个名称创建一个独立的虚拟文件系统（`IFileSystem`）。`GetFileSystemNames()` 和 `GetResourceIndexesFromFileSystem()` 方法分别用于获取所有文件系统名称和计算每个文件系统所包含的资源索引。最终，这些信息被写入 `GameFrameworkVersion.dat` 或 `GameFrameworkList.dat` 文件中，指导运行时的资源加载。

## 自定义构建事件处理器集成

`IBuildEventHandler` 接口为开发者提供了深度集成和扩展构建流程的能力。通过实现此接口，可以创建自定义的构建事件处理器。

一个典型的集成示例如下：

```csharp
public class CustomBuildEventHandler : IBuildEventHandler
{
    public bool ContinueOnFailure => false;

    public void OnPreprocessAllPlatforms(string productName, ...)
    {
        // 在所有平台构建前，执行自定义逻辑，如备份旧版本
        Debug.Log("开始构建所有平台...");
    }

    public void OnPreprocessPlatform(Platform platform, string workingPath, ...)
    {
        // 在特定平台构建前，执行预处理，如生成平台特定的配置文件
        Debug.Log($"开始构建 {platform} 平台...");
    }

    public void OnBuildAssetBundlesComplete(Platform platform, string workingPath, ..., AssetBundleManifest assetBundleManifest)
    {
        // 在AssetBundle构建完成后，可以访问manifest文件
        // 例如，分析AssetBundle的依赖关系并生成报告
    }

    public void OnOutputUpdatableVersionListData(Platform platform, string versionListPath, int versionListLength, int versionListHashCode, int versionListZipLength, int versionListZipHashCode)
    {
        // 在可更新版本列表生成后，可以执行上传到CDN等操作
        Debug.Log($"已生成 {versionListPath}，准备上传...");
    }

    public void OnPostprocessPlatform(Platform platform, string workingPath, ..., bool isSuccess)
    {
        // 在特定平台构建后，执行清理或通知操作
        if (isSuccess)
        {
            Debug.Log($"{platform} 平台构建成功！");
        }
    }

    public void OnPostprocessAllPlatforms(string productName, ...)
    {
        // 在所有平台构建结束后，执行最终的汇总操作
        Debug.Log("所有平台构建完成！");
    }
}
```

要使用此处理器，开发者需要在 `ResourceBuilder` 编辑器窗口中，从下拉菜单中选择 `CustomBuildEventHandler`。`ResourceBuilderController` 会通过反射创建其实例，并在构建流程的各个关键节点调用相应的方法。

## 构建流程扩展与版本策略定制

通过 `IBuildEventHandler`，开发者可以实现高度定制化的版本策略。例如：

1.  **自动化发布**：在 `OnOutputUpdatableVersionListData` 事件中，自动将生成的 `GameFrameworkVersion.dat` 及其关联的资源包上传到指定的 Web 服务器或云存储。
2.  **版本号管理**：在 `OnPreprocessAllPlatforms` 事件中，从外部系统（如 Git）获取最新的版本号，并动态设置 `ApplicableGameVersion`。
3.  **条件化构建**：根据环境变量或命令行参数，在 `OnPreprocessPlatform` 事件中动态调整 `OutputPackageSelected` 或 `OutputFullSelected` 等选项，实现开发版、测试版和正式版的差异化构建。
4.  **构建后验证**：在 `OnPostprocessPlatform` 事件中，对生成的文件进行完整性校验或性能测试，确保构建产物符合发布标准。

这种基于事件的扩展机制，使得 `ResourceBuilderController` 的构建流程既保持了核心的稳定性，又具备了极强的灵活性和可扩展性，能够适应各种复杂的项目需求。
