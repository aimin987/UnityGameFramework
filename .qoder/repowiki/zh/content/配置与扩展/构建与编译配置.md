## 简介
本文档旨在为开发者提供构建与编译配置的实用指南，重点介绍如何通过 `ScriptingDefineSymbols.cs` 文件动态管理不同平台的脚本编译宏（Scripting Define Symbols），以及如何利用 `link.xml` 文件防止Unity在构建时剥离必要的序列化类型和方法。通过这两个工具的结合使用，开发者可以实现功能的条件编译，确保框架核心功能的完整性，并优化构建流程和项目配置。

## 脚本编译宏管理

`ScriptingDefineSymbols.cs` 是一个静态工具类，位于 `Scripts/Editor/Misc/` 目录下，专门用于在Unity编辑器中以编程方式管理脚本编译宏。脚本编译宏是Unity中实现条件编译的关键机制，允许开发者根据不同的构建目标或项目状态包含或排除特定的代码块。

该类支持对多个主流平台（包括独立平台、iOS、Android、WSA和WebGL）进行宏定义的统一管理。其核心功能包括添加、移除和检查宏定义，为自动化构建脚本和持续集成（CI）流程提供了强大的支持。

### 宏定义检查

`HasScriptingDefineSymbol` 方法用于检查指定平台是否已定义某个脚本宏。该方法接受一个 `BuildTargetGroup` 参数和一个宏名称字符串，通过调用Unity的 `PlayerSettings.GetScriptingDefineSymbolsForGroup` API获取当前平台的所有宏定义，并进行字符串匹配。此方法是安全操作，会首先验证输入参数的有效性，避免处理空或null的宏名称。

### 添加宏定义

`AddScriptingDefineSymbol` 方法提供了两种重载形式来添加宏定义。第一种是针对特定平台的重载，它首先检查该宏是否已存在，若不存在则将其添加到当前平台的宏定义列表中，然后通过 `PlayerSettings.SetScriptingDefineSymbolsForGroup` API进行更新。第二种是无平台参数的重载，它会遍历预定义的 `BuildTargetGroups` 数组，为所有支持的平台批量添加同一个宏，极大地简化了跨平台配置的流程。

### 移除宏定义

`RemoveScriptingDefineSymbol` 方法同样提供两种重载，用于从指定平台或所有平台移除一个脚本宏。其实现逻辑与添加操作类似，首先进行存在性检查，然后从宏定义列表中移除目标宏，并更新PlayerSettings。该方法使用 `while` 循环确保所有重复的宏定义都被清除，保证了操作的彻底性。

## 代码剥离保护

Unity的IL2CPP后端在构建过程中会对代码进行剥离（Stripping），以减小最终包体的大小。然而，这种剥离可能会意外移除通过反射或序列化引用的代码，导致运行时错误。`link.xml` 文件正是为了解决这一问题而存在的。

位于 `Libraries/` 目录下的 `link.xml` 文件通过指定需要保留的程序集和命名空间，指导Unity的代码剥离器保留特定的类型和方法。在本项目中，`link.xml` 文件配置了两种保留策略：

```xml
<linker>
  <assembly fullname="GameFramework" preserve="all" />
  <assembly fullname="UnityGameFramework.Runtime" preserve="all" />
</linker>
```

上述配置表示，`GameFramework` 和 `UnityGameFramework.Runtime` 这两个程序集中的所有代码都将被完整保留，不会被剥离。这是一种简洁高效的配置方式，适用于大多数情况。

此外，文件中还注释了一种更细粒度的配置方案，适用于Unity 2017.3之前的版本或需要更精确控制的场景。该方案通过 `<namespace>` 标签，明确列出框架中每一个核心模块的命名空间（如 `GameFramework.Config`, `GameFramework.DataTable` 等），并为它们设置 `preserve="all"` 属性。这种方式虽然配置更繁琐，但提供了更高的灵活性和控制力。

## 综合应用示例

以下是一个结合使用 `ScriptingDefineSymbols.cs` 和 `link.xml` 的典型工作流示例：

1.  **定义开发宏**：在自动化构建脚本中，调用 `ScriptingDefineSymbols.AddScriptingDefineSymbol("DEVELOPMENT_BUILD")` 为所有平台添加 `DEVELOPMENT_BUILD` 宏。在代码中，使用 `#if DEVELOPMENT_BUILD` 来包含调试工具、性能分析器或详细的日志输出。
    ```csharp
    #if DEVELOPMENT_BUILD
        DebuggerComponent.Instance.Show();
    #endif
    ```

2.  **定义发布宏**：对于发布版本，可以添加 `RELEASE_BUILD` 宏，并在代码中启用性能优化或关闭调试功能。
    ```csharp
    #if RELEASE_BUILD
        Application.targetFrameRate = 60;
    #endif
    ```

3.  **保护自定义数据类**：假设项目中有一个名为 `PlayerData` 的自定义数据表类，它通过Unity的序列化系统进行加载。为了防止该类在构建时被剥离，可以在 `link.xml` 中添加相应的保留规则：
    ```xml
    <linker>
      <assembly fullname="Assembly-CSharp">
        <type fullname="PlayerData" preserve="all" />
      </assembly>
    </linker>
    ```
    或者，如果 `PlayerData` 类位于 `MyGame.Data` 命名空间下，可以保留整个命名空间：
    ```xml
    <linker>
      <assembly fullname="Assembly-CSharp">
        <namespace fullname="MyGame.Data" preserve="all" />
      </assembly>
    </linker>
    ```

通过这种方式，开发者可以确保 `PlayerData` 类及其所有公共和私有字段、方法在构建后依然可用，保证了数据加载的正确性。

## 最佳实践

- **使用专用工具类**：像 `ScriptingDefineSymbols.cs` 这样的工具类极大地简化了宏管理，应优先使用，避免在多个地方重复编写类似的PlayerSettings操作代码。
- **合理使用宏**：宏定义应有明确的命名规范（如全大写、使用下划线分隔），并集中管理，避免项目中出现大量难以追踪的临时宏。
- **谨慎配置link.xml**：过度使用 `preserve="all"` 会增加包体大小。应尽量精确地指定需要保留的类型或命名空间，而不是保留整个程序集，除非有充分的理由。
- **版本兼容性**：注意 `link.xml` 的配置语法在不同Unity版本间的差异，确保配置文件与项目使用的Unity版本兼容。
- **自动化集成**：将宏定义的添加和移除操作集成到CI/CD流水线中，根据构建目标（如开发版、测试版、发布版）自动配置编译环境，提高构建的可靠性和一致性。
